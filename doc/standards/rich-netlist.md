# Rich Netlist（RNL）格式标准初稿：原则与边界

状态：原则草案，供讨论；尚未定义可实现的正式语法或发布格式版本。

来源：ChatGPT 对话[《比较原理图网表格式》](https://chatgpt.com/c/6aad54b2-a160-83ea-910a-1edf4a588a40)，2026-09-18。本文于 2026-09-19 整理。

本文保留该对话中用户提出的八项原则，并将最后一轮回复中的细化与补充列为草案建议。对话结束前尚无对这些补充建议的逐项确认；它们不代表已批准的实现契约。早先回复中“精确布局为基础、语义提示为可选”的建议，已由后续讨论推进为“纯语义输入合法，支持混合粒度”。

本文按要求放在 `doc/standards/`，与记录现有产品契约的 `docs/specs/` 区分。Analog Canvas 的导入、导出和渲染支持是后续目标；本文不宣称这些能力已经实现，也不替代现有项目文件格式。

## 1. 定位与总纲

Rich Netlist 是附着于原生电路网表的开放元数据扩展，用于承载原理图的视觉信息，以及指导呈现的电路结构语义和设计意图。

> 原生网表定义电路；Rich Netlist 描述如何理解和呈现这个电路。语义描述可以独立于几何存在，几何可以逐步细化，但两者都不能重新定义电路。

目标是同一份文件可由原有仿真器按原有方式读取，也可由理解 RNL 的工具读取并绘制原理图。扩展信息全部位于宿主语言的合法注释内；剥离注释不应成为仿真前置步骤。

**RNL 是：**

- 附着于原生网表、通过合法注释承载信息的元数据扩展。
- 描述电路结构语义、设计意图和原理图视觉信息的交换格式。
- 允许纯语义、精确几何及混合粒度描述的声明式呈现规范。

**RNL 不是：**

- 统一不同电路网表语言或转换仿真器语法的标准。
- 通过绘图描述创建器件、参数或连接的第二套电路定义。
- 规定唯一布局算法或唯一渲染结果的规范。

## 2. 设计原则

### 2.1 网表兼容性：安全嵌入注释，使用统一子标签

1. **安全存在于原有注释中。** RNL 信息应嵌入原网表的合法注释，被原有仿真器视为普通注释，不影响仿真兼容性。目标覆盖主流电路网表格式，如 SPICE、Spectre、Eldo、HSPICE 等。
2. **注释前缀可不同，子标签保持一致。** 不同网表格式可以采用各自的注释前缀，但注释内部识别 RNL 信息的子标签应统一，例如 `@rnl`。

具体子标签尚未确定。后续定义时需调研并验证，选择在尽可能广泛的已知仿真器和网表格式中均被视为普通注释、不会触发特殊解释的记号；`@rnl` 目前仅为候选。

### 2.2 语义唯一性：电气事实只有一个权威来源

用户原则：扩展不得重复定义或冲突于原网表的连接关系、器件类型、名称和参数；允许显示别名。

草案细化：禁止重复定义电气事实，允许引用、解释和校验电气事实。

| 信息 | 权威边界 |
| --- | --- |
| 器件身份、类型、参数、端子顺序、连接、子电路接口 | 由宿主网表定义，RNL 只引用 |
| 显示别名、文字位置、符号外观、视觉路径 | 由 RNL 描述，不修改电气对象 |
| “M1、M2 构成差分对” | 解释已有对象及其角色，不创建器件或连接 |
| “显示 R1 的参数表达式” | 引用宿主值，不保存另一份权威参数 |
| 自动生成的布局或校验结果 | 派生信息，必须区分来源与有效性 |

RNL 不维护第二份“器件—端子—节点”连接表，也不能为画图加入虚构元件、额外节点或零欧电阻。视觉路径引用现有网络；锚点绑定引用现有端子。发生冲突时，应诊断相关元数据失效，不通过修改电路消除冲突。

### 2.3 可扩展性：小核心与明确边界

用户原则：克制格式细节，为后续扩展及兼容保留空间。

草案建议采用稳定核心、版本化词汇集与能力声明。核心负责身份、引用、作用域、视图、扩展和诊断；结构词汇、符号资源、高级布局约束可以独立演进。减少功能数量不等于省略语义定义；已纳入核心的概念必须有明确规则。

- 未知可选扩展可以不执行；编辑保存时应保留，必要时报告呈现降级。
- 未知必需扩展使受影响视图无法被宣称为完整支持；可以展示明确标记的基础或降级视图。
- 未知坐标变换等会影响其他数据解释的扩展，不能简单跳过后继续假定坐标有效。
- 扩展使用明确命名空间；已知核心结构中的字段拼写错误应报错，不能冒充扩展被静默忽略。

具体版本规则、扩展声明方式与保留机制尚待制定，不承诺任意未来版本都可无损解释。

### 2.4 高层语义：不要求先填写坐标

用户原则：除坐标、朝向、端口位置和走线外，支持 RC 滤波器、差分对、共源放大器，以及对称、匹配、交叉耦合等描述，使 Agent 可以生成语义，由渲染器完成布局。

仅包含结构语义而没有器件坐标，应是合法且完整的一类 RNL 输入。草案建议将相关信息分为三类：

| 类别 | 示例 | 含义 |
| --- | --- | --- |
| 结构描述或断言 | 差分对、RC 网络、交叉耦合 | 解释已有拓扑，可有结构校验前提 |
| 设计意图 | 匹配意图、偏置角色、信号输入角色 | 表达作者目标，不保证电气或物理事实成立 |
| 呈现约束 | 左右对称、信号从左向右、反馈线从下方绕行 | 约束绘图，不改变电路 |

希望匹配、参数相等、物理匹配与视觉对称不能混为同一个无类型属性。

语义结构应具有明确角色，而不只是无序成员集合。例如，差分对描述引用现有两个支路的器件，并分别绑定角色；不重新填写它们的参数或连接。标准词汇需要规定角色、允许引用的对象、可检查前提及能提供的布局信息。

校验结果应允许“成立、冲突、无法确定”。缺少模型、未解析条件分支等情况下，不能将作者的结构标注提升为已验证的工作状态或性能结论。具体词汇与角色名称尚未冻结。

### 2.5 层次化：区分三种范围

用户原则：支持 subcircuit，并以明确的域界定描述范围。

草案建议区分：

- **电气作用域**：确定引用的是谁，遵循宿主的名称和层次规则。子电路定义中的 M1 与某个具体实例内部的 M1 必须可区分。
- **语义分组**：描述对象如何被理解，可以重叠。同一器件属于差分结构、匹配组和偏置组，不意味着重复放置器件。
- **视觉容器**：定义图形包含关系、局部坐标及变换，解决相对于谁绘制。

应预留视图概念，容纳 block、晶体管级及局部信号通路等视图。子电路定义的默认视图与实例的局部覆盖应有明确关系；覆盖图形不改变电气定义。第一版可限制支持范围，但不应将“一份电路只能有一套坐标”固化为基础假设。

### 2.6 混合粒度：约束与逐步细化

用户原则：高层语义与精确坐标可同时存在，渲染逻辑应兼容两者。

草案建议分别表达约束强度与信息来源：硬约束或偏好，作者指定或工具派生。作者锁定的坐标属于约束；自动布局保存的坐标通常属于结果或缓存，不应在再次打开时自动变为最高优先级约束。

可以只固定功能块的位置而让块内自动布局，只规定输入端口在左边，精确指定关键走线的一段，或要求两支路镜像但允许整体平移。

建议的处理原则是先解析作用域与明确的覆盖关系，再共同满足硬约束，随后尽量满足偏好，最后生成尚未指定的几何。不能用“精确坐标总是优先于语义”或文件记录先后顺序暗中解决冲突。同级硬约束不相容时必须诊断；实现应报告未理解或未满足的约束。

### 2.7 精细定义：符号图形、锚点与端子绑定分离

用户原则：默认风格可由渲染器决定，但应允许线条级描述、内嵌或外部引用符号；子电路 block symbol 同样可精确定义。

草案建议将符号拆成图形、几何锚点、锚点到宿主端子的绑定。图形决定外观，锚点决定连接位置，绑定确定所呈现的电气端子。不能从外观推断新增端子，也不能通过自定义 block symbol 增加或重排子电路接口。

允许受限静态 SVG 或等价矢量描述的方向；具体子集尚未决定。资源应不可执行、默认离线可用，不为绘图执行脚本或任意访问网络。外部资源由明确的资源机制解析，并具备版本锁定、内容校验与缺失回退。应支持自包含交付，避免依赖某台机器恰好安装的符号库。

### 2.8 模型友好性：可局部生成与严格校验

用户原则：格式容易被第三方实现和理解，尤其适合 LLM 高正确率地直接生成文本。

草案建议：

- 字段显式、类型明确、含义单一；不依靠记录恰好紧邻某个元件决定归属。
- 允许只补充一个功能块的语义，不要求重写全图或生成大量无必要的标识与坐标。
- 机器语义使用受控词汇；自然语言说明可保留，但不能替代可互操作的定义。
- 校验错误定位到记录、字段、引用或冲突约束，支持局部修复。

可以优先研究可无损映射到 JSON 的数据模型，再评估一种正式文本编码，不急于同时支持 JSON、YAML 和自定义 DSL。若选择 JSON，应明确禁止重复键及依赖对象成员顺序的语义。这些是编码选择建议，不是已经选定 JSON。模型友好性应通过生成和修复实验验证。

## 3. 补充原则与未决问题

以下三项补充原则来自对话中的建议，尚待确认；后续集成边界和标准化问题也仍需进一步设计。

### 3.1 视觉忠实性

图形不能暗示与宿主不同的电路。路径只呈现已有网络，几何交叉本身不定义连接，符号锚点必须绑定正确端子。

完整视图不能因为器件缺少元数据而将其丢弃。局部视图可以省略、折叠或隐藏对象，但应声明展示范围并表达边界连接。无法解析的对象可以显示为未知器件或未解析块，不能静默猜测并标记为已验证。

### 3.2 保真读写与显式失效

只修改 RNL 的操作应默认保留宿主正文和普通注释，不顺便格式化或重新生成不理解的方言语句。这与从编辑器电气模型重新生成网表是不同的操作，未来实现需明确区分。

器件重命名、接口变化或约束失效应产生诊断，不按相似名称自动重绑。派生布局与校验缓存应记录来源和有效性条件；依赖 include 文件、符号资源或实例展开结果时，不能只检查当前文件。无法确认有效性，应重新计算或标记未知。

### 3.3 可测试的互操作性

标准定义可观察契约，不指定唯一渲染器。只给语义而未给完整几何时，不要求不同工具输出像素一致；应检查电气语义保持、引用解析、端子映射、硬约束、未知扩展与读写保留。

精确布局可以保存为视图快照；严格复现还需要固定符号、样式及其他渲染依赖。解析器、校验器、基础绘图器、语义布局器和保真编辑器可以分别声明能力，不能用一个笼统的“支持 RNL”掩盖缺失功能。参考实现的偶然行为不自动成为规范。

### 3.4 Analog Canvas 的后续集成边界

以下是由原则推导的候选验收目标，不是本次实现内容：

| 能力 | 候选验收边界 |
| --- | --- |
| 导入 | 分别解析宿主与 RNL，解析电气引用，保留可保留的信息，报告未知能力、冲突和失效引用 |
| 导出 | 在宿主合法注释中输出元数据；名称、参数和连接仍只由宿主定义；区分保真回写与重新生成 |
| 渲染 | 接受纯语义、精确几何及混合输入；保留端子映射与硬约束；明确局部视图和降级结果 |
| 往返 | 验证宿主语义、作者约束及未知扩展的保留，避免派生坐标被误升级为作者约束 |

集成时需对照现有 [SPICE 前端](../../docs/specs/spice-frontend.md)、[Circuit IR](../../docs/specs/circuit-ir.md)、[原理图模型](../../docs/specs/schematic-model.md)、[连接与布线](../../docs/specs/connectivity-and-routing.md)、[符号 DSL](../../docs/specs/symbol-dsl.md)、[网表导出](../../docs/specs/netlist-export.md)及[项目文件格式](../../docs/specs/project-file-format.md)。

当前导出契约以编辑器模型中的电气事实生成结构网表；当前 Circuit IR 的保留语句也不等于已具备项目级保真往返。RNL 的宿主单源原则约束交换格式，不能直接推断现有持久化模型已经满足其要求。源码保留、身份映射、语义与视图存储，以及与现有渲染风格的衔接，需要另行设计。

### 3.5 后续标准化仍需决定的问题

1. 注释兼容性调研及实测方法：统一子标签是否会触发仿真器的特殊解释，以及各网表格式的安全注释前缀、位置、编码和长度限制；记录覆盖的网表语言、工具版本和解析模式。
2. 正式编码与封装：标签、记录边界、多行形式、版本声明、文件扩展名及诊断定位。
3. 对象引用：大小写、转义、端子标识、定义与实例路径、跨文件引用及重命名行为。
4. 语义词汇：首批结构、角色与可检查前提，未知或不可判定时的行为。
5. 视图与约束：坐标单位、旋转镜像、容器变换、覆盖关系、强度及冲突诊断。
6. 符号资源：静态图形子集、锚点映射、资源寻址、版本与内容校验、缺失回退。
7. 保真与演进：未知扩展的保留粒度、缓存失效、必需能力及版本兼容规则。
8. 互操作验收：宿主透明性、纯语义布局、混合约束、层次引用、精确视图和读写往返的测试语料。

这些问题解决前，不将对话中的示意语法当作解析器契约，也不将草案文档版本当作已发布的 RNL 格式版本。
