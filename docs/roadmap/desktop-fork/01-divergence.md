# 分叉分析

分析固定在 fork [`5231840f`](https://github.com/LXY-freshman/schematic-draft/commit/5231840f31b551f231441976efc0d18e6f9e5f80) 与 upstream [`117ca625`](https://github.com/cascode-ai/analog-canvas/commit/117ca625cd896e2bfeff4bedcb10ba7e480e23b4)，共同起点 [`dbdd9499`](https://github.com/cascode-ai/analog-canvas/commit/dbdd9499659b7606ffbc8cbbe641d2d91f2ffada)。事实来自代码和 Git 历史；“适合共用”“先拆什么”是本次工程判断。

固定基线、可编辑副本和三向 diff 的复现步骤见[目录说明](README.md)。本报告记录该快照的源码事实；后续主线变化须重新核对。

## 1. 差异规模与口径

共同起点之后，主线可达提交 214 个，对方 65 个。提交数不等于功能数。

| 比较方式                   | 变更路径数（不识别 rename） | 含义                             |
| -------------------------- | --------------------------: | -------------------------------- |
| 起点 → fork                |                       1,218 | 对方主动演进                     |
| 起点 → 主线                |                       1,190 | 我方主动演进                     |
| 主线 → fork                |                       1,863 | 当前两个产品的差异               |
| 两边都改过的路径           |                         518 | 潜在适配区，不等于冲突数         |
| 主线新加而 fork 没有的路径 |                         316 | 尚未同步；不能记成 fork 主动删除 |

Git 默认 rename 检测的 `--shortstat` 对方结果是 1,213 个文件、增加 31,335 行、删除 267,055 行；机器索引明确关闭 rename 检测，所以路径数及行数不能和默认统计混用。删掉的 26.7 万行并不全是联网业务，还包括测试、fixtures、工具和文档。

隔离执行 `git merge-tree --write-tree` 返回冲突：416 个路径、417 条冲突消息，其中 313 条 modify/delete、103 条 content、1 条 rename/delete。它只证明整包合并的机械冲突规模；自动合并成功的部分也仍需语义验证。

### 服务边界的具体问题

1. fork `main.ts` 的 `setWindowOpenHandler` 仍对 HTTPS 调用 `shell.openExternal`；因此“严格离线”必须明确是否允许启动系统浏览器。若目标是没有外部联网出口，此通道必须禁用或改为离线帮助。
2. Session 的请求拦截不能代表 Node 主进程、子进程、系统浏览器等所有出口已被限制。本次未做网络抓取验证，不作无泄漏保证。
3. fork [project-files.ts](https://github.com/LXY-freshman/schematic-draft/blob/5231840f31b551f231441976efc0d18e6f9e5f80/apps/desktop/src/project-files.ts) 接受 renderer 给出的 path，并直接 `writeFile` 覆盖目标。可复用的是交互/桥接经验；正式接入应补齐宿主授权的文件句柄、原子替换及外部修改冲突处理，避免把任意路径写入当成通用公开接口。
4. 我方 `apps/local-host` 是本地 Web 宿主，不等于 desktop。桌面第一阶段采用已有的 `app://` 资源服务，不需要再启动一套 HTTP 服务来读写本地项目。将来本地模拟器应另有清晰执行边界。
5. fork 的 `apps/editor/src/README.md` 仍描述已删除的 analytics/Agent 等模块，说明不能把其目录文档当作真实依赖图。此处判断以实际源码为准。

### Visio 并不是零依赖的新增目录

路径归类下 Visio 相关新增 53 个路径，和主线同路径修改重叠为 0；但 [page.ts](https://github.com/LXY-freshman/schematic-draft/blob/5231840f31b551f231441976efc0d18e6f9e5f80/packages/visio/src/page.ts) 调用 `deriveRouteLineJumps`，读取 `profile.nodes.lineJumpRadius`、Route/Instance `strokeScale`。[formula-text.ts](https://github.com/LXY-freshman/schematic-draft/blob/5231840f31b551f231441976efc0d18e6f9e5f80/packages/visio/src/formula-text.ts) 依赖 fork 的 `parseSignalFlowFormulaSegments`；主线已有不同的 `parseSignalFlowInline` 以及富文本 body format。

因此：“没有同名文件冲突”不代表“能在主线编译并正确导出”。底层 OPC/XML/几何部分可先借鉴；上层页面转换必须针对当前模型适配。验收需要真实 Visio 的移动器件、线端跟随、拐点操作和文字编辑，单靠 ZIP/XML 合法性不够。fork 的 [导出契约](https://github.com/LXY-freshman/schematic-draft/blob/5231840f31b551f231441976efc0d18e6f9e5f80/docs/specs/export.md) 和 `scripts/visio-open-check.ps1` 可作为验收起点。

### 属性面板已有好的共用接缝

[component-property-form.tsx](https://github.com/LXY-freshman/schematic-draft/blob/5231840f31b551f231441976efc0d18e6f9e5f80/apps/editor/src/features/properties/component-property-form.tsx) 由 `componentPropertyCodeValue` 取值，经 `serializeComponentPropertyCode`/`parseComponentPropertyCode` 验证，再调统一 `onApply`。Route 也采用同样方式。这说明表单可以作为现有事务入口的另一个 UI，不需要复制编辑内核。

但主线之后新增/调整了 Cell/外部子电路编辑、逻辑门输入数、displayName 与电气名分离、标签格式、Symbol body text 等。应让新表单消费主线当前字段和 planner；不能把 fork 的旧 property-code/planner 整体覆盖回主线。

## 4. 文件协议和保存语义是单独的共享契约分叉

| 项目             | 主线                                                 | fork                                        |
| ---------------- | ---------------------------------------------------- | ------------------------------------------- |
| 内存模型版本     | 58                                                   | 60                                          |
| 当前保存文件版本 | 63                                                   | 60，仍直接序列化旧式完整模型                |
| 58 的含义        | 主线模型边界演进                                     | Route.lineJump                              |
| 59 的含义        | portable owned representation                        | Route/Instance.strokeScale                  |
| 60 的含义        | portable connectivity facts / compact representation | 文档 lineJumpRadiusScale                    |
| 主要扩展名       | `.icproj.json`                                       | `.schdraft`，同时可选择旧 `.icproj.json` 等 |
| Save 目标        | Cloud Project + revision                             | 本机绑定路径                                |

证据：[主线 loader](https://github.com/cascode-ai/analog-canvas/blob/117ca625cd896e2bfeff4bedcb10ba7e480e23b4/packages/project-protocol/src/load.ts)、[portable codec](https://github.com/cascode-ai/analog-canvas/blob/117ca625cd896e2bfeff4bedcb10ba7e480e23b4/packages/project-protocol/src/owned-project-file.ts)、[fork loader](https://github.com/LXY-freshman/schematic-draft/blob/5231840f31b551f231441976efc0d18e6f9e5f80/packages/project-protocol/src/load.ts)、[fork writer](https://github.com/LXY-freshman/schematic-draft/blob/5231840f31b551f231441976efc0d18e6f9e5f80/packages/project-protocol/src/save.ts)。

主线 `load.ts` 将版本 ≥59 送入 portable decoder，fork 的 59/60 没有这些结构。不能只改版本号让它进入读入流程，也不能认为改扩展名就解决 JSON 协议冲突。现阶段有拒绝保护；本次没有证明“必然静默读错”。

已发布的 fork 文件需要显式来源转换入口及 fixture。独立 fork 以后可用自己的格式标识和版本空间；官方 Web/desktop 则统一使用主线 `project-protocol`。产品版本、内存模型版本、文件格式版本必须分开管理。

正式 Save 的区别也不是把 `fetch` 换成 `writeFile`：主线有 cloud revision 冲突、多个标签页、导出/发布安全快照，desktop 有 Save As、路径授权、磁盘错误、外部修改、关闭窗口。这些结果需要共同的状态协调和不同的具体实现。

## 5. 两边都变的耦合点

重点是 `App.tsx`、`use-project-file-lifecycle.ts`、Editor chrome/docks、Properties parser/planner 和 portable codec。fork 的 App 相对起点增删约 2,030 行，lifecycle 约 415 行；它们同时包含能力删除、功能接线和交互改变。

主线在这些区域还增加了 workspace/tabs、后台 Agent Project binding、源连接快照、标签和复制修复。因此迁入应以当前主线为底座，抽出宿主接缝，再逐项适配功能。不能以较小的 fork App 替换主线 App，然后逐个补回线上能力。

## 6. 测试与发布也发生了分叉

fork 移除了原有 CI/部署门禁，使用本地验证和手工打包；这来自其仓库规则和脚本，并不等于没有测试。它确实有 Properties、跳线、Visio、文件桥接和窗口脚本。

主线的 merge queue、Core contracts、Browser tests、Test-Impact 与 Production 验证必须保留。导入功能时把有价值的测试接进主线对应层；不复制 fork 的 CI 删除和主线测试删减。

源码中找到了离线控制实现；没有找到覆盖所有网络出口的打包产物自动化回归。安全承诺、实际 EXE 行为、Visio 可编辑性仍是后续验收条件。
